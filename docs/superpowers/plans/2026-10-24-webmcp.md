# WebMCP Exploration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Expose site content (profile, skills, projects, blog, resources) as WebMCP tools on porfirio.dev, exploring the full WebMCP surface (imperative read-only, interactive, state-reflecting, and declarative form APIs) as a learning experiment.

**Architecture:** A thin `src/lib/webmcp/` module feature-detects `document.modelContext.registerTool` (current spec) and `navigator.modelContext.provideContext` (earlier draft), exposing a Svelte 5 rune-based `useWebMCP(() => tools)` composable. Each route registers its own tools; the composable handles re-registration on state change and cleanup via `AbortSignal` on navigation. Prerequisite: site content (skills, projects, profile) moves from hardcoded markup into typed data modules so tools can return real data. Everything is client-side and a no-op without browser support.

**Tech Stack:** Svelte 5 (runes), SvelteKit 3, TypeScript strict, `webmcp-types` (0.1.x), Vitest (via Vite+), pnpm.

**Spec:** `docs/superpowers/specs/2026-10-24-webmcp-design.md`

## Global Constraints

- Zero visible change for users without WebMCP: no API → all registration is a no-op; pages render exactly as today.
- Tool names: snake_case, ASCII `[a-z0-9_-]`, ≤128 chars (spec constraint).
- Read-only tool results include absolute URLs (`https://porfirio.dev/...`) so agents can cite them.
- `webmcp-types` at 0.1.x: if its types conflict with the live API, fall back to minimal local types in `src/lib/webmcp/types.ts` (documented decision, not a blocker).
- Follow repo formatting/lint: `pnpm fmt`, `pnpm lint`, `pnpm check`, `pnpm test` must pass. `vp fmt` uses single quotes, printWidth 100.
- Two-commit separation per spec: commit 1 is data extraction only; WebMCP code comes after.
- SSR safety: `document`/`navigator` access only inside client guards (`browser` from `$app/environment` or `typeof document !== 'undefined'`).

## Review Focus

- **SSR/prerender crash:** `/about`, `/skills`, `/projects`, `/resources` are prerendered; any module-level `document` access breaks `pnpm build`. Expect: build succeeds, HTML identical modulo the new filter UI markup. Tested by `pnpm build` in Task 7 and by keeping detection inside functions (Task 2 tests the no-document fallback).
- **No-op in unsupported browsers:** expect no console errors, no thrown exceptions, no UI change when `modelContext` is absent. Tested in Task 2 (`returns null when no API exists`).
- **Re-registration leaks:** `useWebMCP` re-runs on state change; expect no duplicate tool registrations and cleanup on unmount (AbortSignal aborted). Tested in Task 2 (`registers each tool with its own AbortSignal` / `cleanup aborts all signals`).
- **Skills page visual parity:** data extraction must render the identical three lists. Expect byte-equivalent rendered content (aside from added filter UI in Task 5). Checked by comparing `/skills` markup before/after in Task 1 (`pnpm build` + diff of rendered HTML) and by a data-shape unit test.
- **Blog remote queries in browser:** `getBlogPosts`/`getBlogTags` are `$app/server` queries; on the non-prerendered blog routes they run client-side after hydration. Expect the blog tools to resolve with real post data in the browser. Verified manually (documented in Task 7's testing doc); no unit test possible without a running server.

### Task 2: WebMCP core module (`model-context.ts` + `use-webmcp`)

**Files:**

- Create: `src/lib/webmcp/model-context.ts`

- Create: `src/lib/webmcp/index.ts`
- Modify: `package.json` (add `webmcp-types` dependency)

**Interfaces:**

- Consumes: nothing.
- Produces (consumed by Tasks 3–6):
  - `src/lib/webmcp/index.ts`: re-exports `useWebMCP`, `type WebMCPTool`.
  - `model-context.ts`:
    - `type WebMCPTool = WebMCP.ModelContextTool` (from `webmcp-types`; fall back to a local minimal type if the package's global augmentation conflicts — document in a code comment).
    - `export function getModelContext(): WebMCP.ModelContext | null` — returns `document.modelContext` if present, else `navigator.modelContext` cast into the same type (earlier draft shape), else `null`. Client-only; never throws.
    - `export function registerTools(tools: WebMCPTool[]): () => void` — for the `document.modelContext` shape: `registerTool(tool, { signal })` per tool, one `AbortController` per tool; returns a cleanup fn that aborts all. For the `navigator.modelContext` `provideContext` shape: call `provideContext({ tools })`; cleanup calls `provideContext({ tools: [] })`. Returns no-op cleanup when unsupported. Registration promise rejections are caught and logged via `console.warn` (permission-policy denials).
  - `use-webmcp.svelte.ts`: `export function useWebMCP(toolFactory: () => WebMCPTool[], options?: { enabled?: boolean }): { supported: Svelte<boolean> }` — `$effect` calls `registerTools(toolFactory())` and cleans up on re-run/destroy; `supported` is a readable rune set once on mount (`getModelContext() !== null`). No-op when `enabled === false` or SSR.
