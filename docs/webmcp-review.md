# WebMCP PR (#38) — second-opinion review

Scope: 30 files, `src/lib/webmcp/*`, data extraction (skills/projects/profile), per-route `useWebMCP` calls, and the declarative `BlogSearch` form. Baseline: `vp test` passes (30 tests).

Overall: the architecture is sound. Per-route registration, an adapter over both API shapes, the SSR guard, a "never break the page" error policy, and pure tool factories with unit tests are all good choices. The findings below are concrete and small.

## Findings

| #   | Severity | Where                                | Issue                                                                                                                                                                                                                   | Fix                                                                                                                                                         |
| --- | -------- | ------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | High     | `BlogSearch.svelte`                  | `toolname`/`tooldescription` are on the `<input>`. The declarative API reads them from the `<form>`, so the tool is never registered (Copilot review).                                                                  | Move both attributes to `<form>`. Keep `name="q"` on the input. Add `toolparamdescription` on the input.                                                    |
| 2   | High     | `BlogSearch.svelte`                  | The submit handler cancels navigation but never calls `event.respondWith()`. Agent-invoked submissions get no result (Copilot review).                                                                                  | If `event.agentInvoked` and `respondWith` exist, call `event.respondWith(Promise.resolve(summary))` after applying the filter. Human submits are unchanged. |
| 3   | Medium   | `model-context.ts` `registerTools`   | The `registerTool` branch only guards the async rejection. A synchronous throw (e.g. duplicate name, `InvalidStateError`) would escape the `$effect` and break the page. The last commit guarded only `provideContext`. | Wrap each `registerTool` call in try/catch with a `console.warn`.                                                                                           |
| 4   | Medium   | `use-webmcp.svelte.ts`               | `supported` is a `$state` that is never reassigned. It is a plain constant dressed as reactive, and nothing consumes it.                                                                                                | Make it a plain `const` computed once. Keep the return shape.                                                                                               |
| 5   | Medium   | `model-context.ts` `getModelContext` | The `provideContext` adapter has a stateful tool list and is used only for the `supported` check. It is dead weight, and its `registerTool` ignores `signal`.                                                           | Replace with `isWebMCPSupported(): boolean` built on `detectContext()`. Delete `getModelContext` and its tests, or rewrite those tests.                     |
| 6   | Medium   | `blog/+page.svelte`, `blog-tools.ts` | The match logic (title or tag, case-insensitive) is duplicated. The page and the tool can drift.                                                                                                                        | Export `filterPosts(posts, query)` from `blog-tools.ts` and use it in both. Add a test.                                                                     |
| 7   | Low      | `[...slug]/+page.svelte`             | The `get_current_article` tool is defined inline in the route, unlike every other tool. It is untested.                                                                                                                 | Move it to `blog-tools.ts` as `getCurrentArticleTool(getPost)`. Add a test.                                                                                 |
| 8   | Low      | `blog/+page.svelte`                  | The `$effect` plus `posts.then` plus `alive` flag hand-rolls the hydration of `clientPosts`.                                                                                                                            | Keep the behaviour, but note it in the PR. It is acceptable, and not worth changing without an end-to-end check.                                            |
| 9   | Low      | tools                                | `execute(input: Record<string, unknown>)` re-validates by hand in each tool.                                                                                                                                            | Acceptable at this size. Revisit if the tool count grows.                                                                                                   |
| 10  | Low      | `tools.ts`                           | `SITE_ORIGIN` is hard-coded. Preview deploys will cite production URLs.                                                                                                                                                 | Intentional (canonical URLs). Document it, no change.                                                                                                       |
